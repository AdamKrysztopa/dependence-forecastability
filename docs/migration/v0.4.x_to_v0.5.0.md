# Migration Guide: v0.4.x → v0.5.0

This guide covers all breaking changes introduced in v0.5.0 and provides a
one-to-one migration recipe for each.

> **Quick summary of breaking changes:**
> - Default AMI estimator changed from KSG-I (sklearn) to KSG-II (Chebyshev). Pass `estimator='ksg1_sklearn'` to reproduce v0.4.3 numerics.
> - `compute_transfer_entropy` removed; replaced by `compute_transfer_entropy_ksg` (true TE) and `compute_predictive_information_gain` (residual-MI).
> - Significance correction now defaults to Romano-Wolf FWER. Pass `correction='none'` to reproduce v0.4.3 per-lag behaviour.
> - Physical `src/forecastability/domain/` package replaces the allowlist-virtual layer; import paths for 22 modules have changed.

## 7. `n_surrogates` default raised from 99 to 999 (RVH-F18)

**What changed:** `TriageRequest()` constructed with no arguments now uses
`n_surrogates=999` instead of `n_surrogates=99`.

**Who is affected:** Code that relied on the old default to control runtime cost.
Triage runs will be ~3–4× slower by default (the batched FFT vectorization from
RVH-F04 means 10× more surrogates cost only ~3–4× wall-clock).

**Who is NOT affected:** Code that passes `n_surrogates` explicitly — e.g.
`TriageRequest(series=..., n_surrogates=99)` is unaffected and still accepted
without error (the `ge=99` floor is unchanged).

```python
# Before v0.5.0 — TriageRequest() defaulted to n_surrogates=99
req = TriageRequest(series=ts)   # n_surrogates was 99

# After v0.5.0 — default is 999; to reproduce old speed, pass explicitly
req = TriageRequest(series=ts, n_surrogates=99)  # still valid, ge=99 floor unchanged
```

**What did NOT change:** The `ge=99` validation floor is unchanged.
`TriageRequest(n_surrogates=98)` still raises `ValidationError`.

## 8. `compute_pami_linear_residual` emits `UserWarning` on low-cardinality input (RVH-F21)

**What changed:** When `unique(X) / N < 0.1`, `compute_pami_linear_residual` now
emits a `UserWarning` describing the approximation risk.  The computation
continues without rerouting — the linear-residual approximation is already a
Gaussian-assumption model, so rerouting to GCMI would not reduce the error further.

**Who is affected:** Pipelines with low-cardinality (discrete/ordinal) inputs that
previously ran silently.

```python
import warnings

# Suppress if you have already acknowledged the limitation
with warnings.catch_warnings():
    warnings.filterwarnings("ignore", message=".*low cardinality.*")
    result = compute_pami_linear_residual(integer_series, max_lag=20)
```

## 9. `signal_to_noise` renamed to `informative_mass_fraction` (RVH-F23)

**Failure mode:** `AttributeError: signal_to_noise was renamed to informative_mass_fraction in v0.5.0; see docs/migration/v0.4.x_to_v0.5.0.md`

**Affected types:** `AmiInformationGeometry`, `ForecastabilityFingerprint`

**Also affected:** `RoutingRecommendation.caution_flags` — the flag value `"low_signal_to_noise"` is now `"low_informative_mass_fraction"`.

**Before:**
```python
result = compute_ami_information_geometry(series, max_lag=20)
print(result.signal_to_noise)  # AttributeError in v0.5.0
```

**After:**
```python
result = compute_ami_information_geometry(series, max_lag=20)
print(result.informative_mass_fraction)  # fraction of lags with corrected AMI above surrogate threshold
```
