# Migration Guide: v0.4.x → v0.5.0

This guide covers all breaking changes introduced in v0.5.0 and provides a
one-to-one migration recipe for each.

> **Quick summary of breaking changes:**
> - Default AMI estimator changed from KSG-I (sklearn) to KSG-II (Chebyshev). Pass `estimator='ksg1_sklearn'` to reproduce v0.4.3 numerics.
> - `compute_transfer_entropy` removed; replaced by `compute_transfer_entropy_ksg` (true TE) and `compute_predictive_information_gain` (residual-MI).
> - Significance correction now defaults to Romano-Wolf FWER. Pass `correction='none'` to reproduce v0.4.3 per-lag behaviour.
> - Physical `src/forecastability/domain/` package replaces the allowlist-virtual layer; import paths for 22 modules have changed.

## 1. Default AMI estimator changed to KSG-II

**What changed:** `compute_ami(series, max_lag=20)` now uses the Chebyshev
KSG-II estimator (unified `KSG2CurveKernel`) by default.  Results will differ
from v0.4.3 by a few percent on typical inputs.

**Who is affected:** Any code that stores or compares raw AMI / pAMI values
produced by `compute_ami`, `compute_pami_linear_residual`,
`compute_ami_information_geometry`, or any surrogate-band scorer without
explicitly passing `estimator='ksg1_sklearn'`.

**Before (v0.4.3 — KSG-I via sklearn):**
```python
from forecastability import compute_ami

# v0.4.3 default was KSG-I; results differ from v0.5.0 default
ami_curve = compute_ami(series, max_lag=20)
```

**After (v0.5.0 — reproduce v0.4.3 numerics):**
```python
from forecastability import compute_ami

# Pass estimator='ksg1_sklearn' to reproduce v0.4.3 bit-identical results
ami_curve = compute_ami(series, max_lag=20, estimator="ksg1_sklearn")
```

**After (v0.5.0 — use new default KSG-II):**
```python
from forecastability import compute_ami

# KSG-II is the new default; no argument needed
ami_curve = compute_ami(series, max_lag=20)
```

## 2. `compute_transfer_entropy` removed

**What changed:** `compute_transfer_entropy` has been removed.  Importing it
now raises `ImportError` with a migration recipe.  Two replacement functions
ship under honest names:

- `compute_transfer_entropy_ksg` — true Schreiber transfer entropy via the
  Frenzel-Pompe KSG-CMI estimator.
- `compute_predictive_information_gain` — the v0.4.3 residual-MI estimator,
  renamed to reflect what it actually computes.

**Before (v0.4.3 — this import raises ImportError in v0.5.0):**
```python
# v0.4.3 only — raises ImportError in v0.5.0
# from forecastability import compute_transfer_entropy  # noqa: ERA001
```

**After (v0.5.0 — true Schreiber TE via KSG-CMI):**
```python
import numpy as np
from forecastability import compute_transfer_entropy_ksg

rng = np.random.default_rng(42)
source = rng.standard_normal(300)
target = rng.standard_normal(300)
# compute_transfer_entropy_ksg(source, target, lag) — source drives target
result = compute_transfer_entropy_ksg(source, target, lag=3)
print(result.status, result.quality_warning)
```

**After (v0.5.0 — legacy residual-MI under honest name):**
```python
import numpy as np
from forecastability import compute_predictive_information_gain

rng = np.random.default_rng(42)
source = rng.standard_normal(300)
target = rng.standard_normal(300)
# lag is keyword-only; source and target are positional
result = compute_predictive_information_gain(source, target, lag=3)
print(result.status)
```

## 3. Significance correction now defaults to Romano-Wolf

**What changed:** The surrogate significance band now applies Romano-Wolf
step-down FWER correction across lags by default.  The `SignificanceCorrectionService`
accepts `correction: Literal["romano_wolf", "bh", "by", "none"]`.

**Who is affected:** Code that calls `SignificanceCorrectionService` directly
or compares threshold-crossing lag counts from v0.4.3 baselines.  The
Romano-Wolf corrected mask is typically more conservative than the v0.4.3
per-lag uncorrected mask: fewer lags will exceed the significance threshold.

**Note:** `TriageRequest` / `run_triage` apply Romano-Wolf by default.  The
`correction` parameter is available at the `SignificanceCorrectionService`
level for lower-level usage.

**After (v0.5.0 — Romano-Wolf FWER; no change to TriageRequest call site):**
```python
from forecastability import TriageRequest, run_triage
import numpy as np

rng = np.random.default_rng(42)
series = rng.standard_normal(200)

# Romano-Wolf is applied internally; the call site is unchanged
result = run_triage(
    TriageRequest(
        series=series,
        max_lag=20,
        n_surrogates=99,
        random_state=42,
    )
)
```

**Lower-level usage — controlling correction mode directly:**
```python
from forecastability.services.significance_correction_service import (
    SignificanceCorrectionService,
)
import numpy as np

# correction='none' reproduces v0.4.3 per-lag uncorrected behaviour
svc = SignificanceCorrectionService(correction="none", alpha=0.05)
# svc = SignificanceCorrectionService(correction="romano_wolf", alpha=0.05)
```

## 4. Domain module import paths changed

**What changed:** 18 modules previously accessible via
`forecastability.triage.*`, `forecastability.utils.*`, and other non-domain
paths have been moved into `src/forecastability/domain/`.  The public facade
(`from forecastability import ...`) is unaffected for names on the stable API
surface.  Deep imports of internal paths will break.

**Who is affected:** Code that directly imports from internal module paths
such as `forecastability.triage.models`, `forecastability.utils.aggregation`,
or `forecastability.triage.readiness`.  Code using only the top-level
`forecastability` facade or `forecastability.triage` public re-exports is
**not** affected.

**Before (v0.4.3 — deep import; may raise ImportError in v0.5.0):**
```python
# v0.4.3 internal path — may not resolve in v0.5.0
# from forecastability.triage.models import TriageResult  # noqa: ERA001
```

**After (v0.5.0 — use the stable public facade):**
```python
# Always use the stable public facade; unchanged in v0.5.0
from forecastability import TriageResult
```

## 5. Agent adapter module paths changed

**What changed:** `adapters/agents/` and `adapters/llm/` have been merged into
`adapters/agents/{payloads,runtime}/`.  The deprecated shim
`adapters/pydantic_ai_agent.py` is **removed** — importing it raises
`ImportError` with a migration recipe.

**Who is affected:** Code that imports agent tool classes directly from
`forecastability.adapters.llm.*` or the old shim path.

**Before (v0.4.3 — these imports raise ImportError in v0.5.0):**
```python
# v0.4.3 only — raises ImportError in v0.5.0
# from forecastability.adapters.pydantic_ai_agent import ...  # noqa: ERA001
# from forecastability.adapters.llm.triage_agent import ...   # noqa: ERA001
```

**After (v0.5.0):**
```python
from forecastability.adapters.agents.runtime import TriageAgent
from forecastability.adapters.agents.payloads import TriageAgentPayload
```

## 6. Public API surface shrunk

**What changed:** `forecastability.__init__` now re-exports only from
`forecastability.api` (approximately 25 curated public names).  Names that
were previously importable from `forecastability` but are not on the stable
API surface now live in `forecastability._legacy` and emit a
`DeprecationWarning` on access for one release cycle before removal.

**Who is affected:** Code that imports names not listed in
`docs/public_api.md`.  If you see a `DeprecationWarning` about a symbol,
update the import to the new canonical path listed in the warning message.

**After (v0.5.0 — use only names listed in `docs/public_api.md`):**
```python
# Use only names on the stable public surface
from forecastability import run_triage, TriageRequest, TriageResult
```

## 7. `n_surrogates` default raised from 99 to 999 (RVH-F18)

**What changed:** `TriageRequest()` constructed with no arguments now uses
`n_surrogates=999` instead of `n_surrogates=99`.

**Who is affected:** Code that relied on the old default to control runtime cost.
Triage runs will be ~3–4× slower by default (the batched FFT vectorization from
RVH-F04 means 10× more surrogates cost only ~3–4× wall-clock).

**Who is NOT affected:** Code that passes `n_surrogates` explicitly — e.g.
`TriageRequest(series=..., n_surrogates=99)` is unaffected and still accepted
without error (the `ge=99` floor is unchanged).

```python
# Before v0.5.0 — TriageRequest() defaulted to n_surrogates=99
req = TriageRequest(series=ts)   # n_surrogates was 99

# After v0.5.0 — default is 999; to reproduce old speed, pass explicitly
req = TriageRequest(series=ts, n_surrogates=99)  # still valid, ge=99 floor unchanged
```

**What did NOT change:** The `ge=99` validation floor is unchanged.
`TriageRequest(n_surrogates=98)` still raises `ValidationError`.

## 8. `compute_pami_linear_residual` emits `UserWarning` on low-cardinality input (RVH-F21)

**What changed:** When `unique(X) / N < 0.1`, `compute_pami_linear_residual` now
emits a `UserWarning` describing the approximation risk.  The computation
continues without rerouting — the linear-residual approximation is already a
Gaussian-assumption model, so rerouting to GCMI would not reduce the error further.

**Who is affected:** Pipelines with low-cardinality (discrete/ordinal) inputs that
previously ran silently.

```python
import warnings

# Suppress if you have already acknowledged the limitation
with warnings.catch_warnings():
    warnings.filterwarnings("ignore", message=".*low cardinality.*")
    result = compute_pami_linear_residual(integer_series, max_lag=20)
```

## 9. `signal_to_noise` renamed to `informative_mass_fraction` (RVH-F23)

**Failure mode:** `AttributeError: signal_to_noise was renamed to informative_mass_fraction in v0.5.0; see docs/migration/v0.4.x_to_v0.5.0.md`

**Affected types:** `AmiInformationGeometry`, `ForecastabilityFingerprint`

**Also affected:** `RoutingRecommendation.caution_flags` — the flag value `"low_signal_to_noise"` is now `"low_informative_mass_fraction"`.

**Before:**
```python
result = compute_ami_information_geometry(series, max_lag=20)
print(result.signal_to_noise)  # AttributeError in v0.5.0
```

**After:**
```python
result = compute_ami_information_geometry(series, max_lag=20)
print(result.informative_mass_fraction)  # fraction of lags with corrected AMI above surrogate threshold
```

---

## What did NOT change

The following behaviours are **identical** in v0.5.0 to v0.4.3:

- **Numerics with `estimator='ksg1_sklearn'`** — passing
  `estimator='ksg1_sklearn'` to any public AMI / pAMI surface reproduces
  v0.4.3 values bit-identically.  The regression fixtures in
  `docs/fixtures/v0_5_0_regression/` verify this.

- **`correction='none'`** — passing `correction='none'` to any surface that
  accepts it reproduces v0.4.3 per-lag uncorrected significance behaviour.

- **`forecastability_profile` numerics with both compatibility opts** —
  calling `compute_ami_information_geometry(series, estimator='ksg1_sklearn',
  correction='none')` produces output identical to v0.4.3.

- **Explicit `n_surrogates=99`** — `TriageRequest(series=...,
  n_surrogates=99)` is still accepted without error; the `ge=99` validation
  floor is unchanged.  Only the *default* rose to 999.

- **`ForecastPrepContract` schema** — the contract fields, serialization,
  and `model_dump_json()` surface are unchanged.

- **`run_triage` return type** — `TriageResult` structure, field names, and
  `blocked` / `readiness` / `interpretation` fields are unchanged.

- **`generate_ar1`, `generate_fingerprint_archetypes`, and all
  data-generation helpers** — outputs are deterministic and unchanged.

- **CLI entry points** — `forecastability triage`, `forecastability extended`,
  and `forecastability fingerprint` command signatures are unchanged.
